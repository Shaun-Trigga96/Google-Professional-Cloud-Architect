# Designing Reliable Systems

## Key Performance Metrics for Reliable Systems

- **Availability**: The percent of time a system is running and able to process requests.
  - Monitoring is vital for high availability.
  - Health checks can detect when an application reports that it is okay.
  - Detailed monitoring of services using white box metrics to count traffic successes and failures helps predict problems.
  - Building in fault tolerance by removing single points of failure improves availability.
  - Backup systems also play a key role in improving availability.

- **Durability**: The chance of losing data due to hardware or system failure.
  - Ensuring data is preserved and available involves replication and backup.
  - Data can be replicated in multiple zones.
  - Regular restores from backup should be performed to confirm the process works as expected.

- **Scalability**: The ability of a system to continue to work as user load and data grow.
  - Monitoring and autoscaling should be used to respond to variations in load.
  - Metrics for scaling can be standard metrics like CPU or memory, or custom metrics like the number of players on a game server.

## Designing for Reliability

- **Avoid Single Points of Failure**:
  - Replicate data and create multiple virtual machine instances.
  - Define your unit of deployment and understand its capabilities.
  - Deploy two extra instances (N plus two) to handle both failure and upgrades.
  - Deployments should ideally be in different zones to mitigate zonal failures.

- **Upgrade Considerations**:
  - Load balance three BMs to achieve N plus two.
  - If one is being upgraded and another fails, 50% of the available capacity is removed, potentially doubling the load on the remaining instance.
  - Capacity planning and knowing the capability of your deployment unit is important.
  - Make deployment units interchangeable, stateless clones for ease of scaling.

- **Correlated Failures**:
  - Occur when related items fail at the same time.
  - Examples: single machine failure, top-of-rack switch failure, zone or region loss, software faults, configuration data failure.
  - Group of related items that could fail together is referred to as a failure or fault domain.
  - Techniques to avoid correlated failures:
    - Be aware of failure domains.
    - Decouple servers using microservices distributed among multiple failure domains.
    - Divide business logic into services based on failure domains and deploy to multiple zones/regions.
    - Split responsibilities into components and spread these over multiple processes.

- **Microservices Design**:
  - Design should result in loosely coupled, independent but collaborating services.
  - A failure in one service should not cause a failure in another service.
  - Collaborating service may have reduced capacity but remains in control.

- **Cascading Failures**:
  - Occur when one system fails, causing others to be overloaded and subsequently fail.
  - Example: message queue overloaded because a backend fails.
  - Avoid cascading failures with support from the deployment platform:
    - Use health checks in Compute Engine or readiness and liveliness probes in GKE.
    - Ensure new instances start fast and do not rely on other backends or systems to start up.

- **Query of Death**:
  - A request made to a service causes a failure in the service due to an error in business logic.
  - Requires good monitoring, observability, and logging to determine the root cause.
  - Monitor latency, resource utilization, and error rates to identify the problem.

- **Positive Feedback Cycle Overload Failure**:
  - Caused by trying to prevent problems by adding retries in the event of a failure.
  - Intelligent retries using feedback from the failing service:
    - Use exponential backoff pattern: wait longer between retry attempts.
    - Limit the number of tries and the length of time before giving up.
    - Example: wait 1 second plus a random number of milliseconds, then 2 seconds, then 4 seconds, etc.

- **Circuit Breaker Pattern**:
  - Protects the service from too many retries.
  - Monitors the service health and stops forwarding requests if the service is not healthy.
  - When the service becomes operational again, it begins feeding requests in a controlled manner.
  - Istio service mesh in GKE automatically implements circuit breakers.

- **Lazy Deletion**:
  - Builds in the ability to reliably recover data when a user deletes it by mistake.
  - Deletion pipeline progresses in phases:
    - User deletes data, can be restored within a predefined time period (e.g., 30 days).
    - After the period, data moves to the soft deletion phase, can be restored by user support or administrators.
    - After the soft deletion period (e.g., 15, 30, 45, or 60 days), data is deleted and no longer available.
    - Restoration only possible through backups or archives.

## Disaster Planning

- **High Availability**:
  - Deploy to multiple zones in a region.
  - Use Compute Engine regional instance groups for built-in functionality to keep instances running.
  - Use auto healing with an application health check and load balancing to distribute load.
  - Storage solution affects high availability needs:
    - Cloud SQL can be configured for high availability with data redundancy and a standby instance in another zone.
    - Firestore and Spanner provide high availability by default.

- **Google Cloud Services**:
  - Regional managed instance groups distribute VMs across zones.
  - Choose between single zones and multiple zones or regional configurations for instance groups.
  - Google Kubernetes Engine clusters can be deployed to single or multiple zones.
  - Regional clusters increase availability by replicating master and nodes across multiple zones.

- **Health Checks**:
  - Create a health check endpoint to indicate service availability and readiness.
  - Health checks should confirm the availability of dependent back-end services.
  - If a health check fails, the instance group removes the failing instance and creates a new one.
  - Load balancers use health checks to determine which instances to send requests to.

- **High Availability for Data Storage and Database Services**:
  - Google Cloud Storage: Achieve high availability with multi-region storage buckets.
  - Cloud SQL: Create a failover replica for high availability.
  - Firestore and Spanner: Offer single and multi-region deployments with high availability.

- **Cost Considerations**:
  - Deploying for high availability increases costs due to extra resources.
  - Consider the cost of resources and the cost of service downtime.
  - Assess risk versus cost by balancing deployment options against the cost of being down.

- **Disaster Recovery Strategies**:
  - **Cold Standby**:
    - Create snapshots of persistent disks, machine images, and data backups.
    - Store snapshots in multi-region storage.
    - Spin up services in the backup region using snapshot images and persistent disks.
    - Document and test recovery procedures regularly.

  - **Hot Standby**:
    - Instance groups in multiple regions with traffic forwarded by a global load balancer.
    - Implement for data storage services like multi-regional Cloud Storage buckets and database services like Spanner and Firestore.

- **Recovery Metrics**:
  - **Recovery Point Objective (RPO)**: Amount of data acceptable to lose.
  - **Recovery Time Objective (RTO)**: Time to be back up and running.
  - Brainstorm scenarios causing data loss or service failures and prioritize them.
  - Create a recovery plan based on disaster scenarios, risk, RPO, and RTO.
  - Communicate and test recovery procedures regularly.

- **Backup Strategy**:
  - Capture information on backup strategy, location of backups, and recovery procedures.
  - Prepare a team for disaster using drills.
  - Document and practice plans for addressing potential system failures.
  - Assess risks and balance costs of availability against the cost of unavailability.
