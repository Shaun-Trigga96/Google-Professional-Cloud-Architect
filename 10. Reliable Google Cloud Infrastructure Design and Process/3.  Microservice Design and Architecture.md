# Microservices in Detail

## Overview

- **Microservices**: Divide a large program into smaller, independent services.
- **Monolithic Applications**: Implement all features in a single code base with a shared database.

## Industry Trends

- Microservices are the current industry trend.
- Importance of selecting this architecture for valid reasons.

## Primary Reasons for Microservices

- Enable teams to work independently and deliver at their own pace.
- Support organizational scaling by adding more teams.
- Ability to scale microservices independently based on requirements.

## Architectural Considerations

- Applications should be composed of modular components with clearly-defined boundaries.
- **Monolith**: All components are packaged and deployed together.
- **Microservices**: Individual components are deployable.

## Google Cloud Services for Microservices

- **App Engine**
- **Cloud Run**
- **GKE (Google Kubernetes Engine)**
- **Cloud Functions**

## Independence of Services

- Each service should have its own datastore.
- Avoid coupling between services through a shared datastore.

## Goals of Microservice Architecture

- Define strong contracts between microservices.
- Allow independent deployment cycles, including rollback.
- Facilitate concurrent A/B release testing on subsystems.
- Minimize test automation and quality assurance overhead.
- Improve clarity of logging and monitoring.
- Provide fine-grained cost accounting.
- Increase application scalability and reliability.

## Challenges of Microservice Architecture

- Defining clear boundaries between services.
- Increased infrastructure complexity with more points of failure.
- Increased latency and need for resilience.
- Security for service-to-service communication.
- Managing and versioning service interfaces.
- Maintaining backward compatibility.

## Decomposing Applications into Microservices

- Techniques like domain-driven design for identifying logical functional groupings.
- Decompose by feature or functional groupings to minimize dependencies.
- Example: Online retail application with groupings like product management, reviews, accounts, and orders.
- Shared services like authentication should be isolated and deployed separately.

## Designing Microservices

- Stateless services are easier to manage, scale, and migrate.
- Stateful services introduce challenges in scaling and upgrading.
- Importance of state management in early design stages.

## Best Practices for Stateful Services

- Avoid in-memory shared state to maintain benefits of microservices.
- Use backend storage services shared by frontend, stateless services.
- Examples: Firestore, Cloud SQL for persistent state; Memorystore for caching.

## General Solution Layout

- Load balancer distributes load between backend and frontend services.
- Backend can scale to meet frontend demand.
- Isolate stateful services and use persistent storage and caching.
- Leverage scalability and fault tolerance of Google Cloud Services for stateless services.
- Limit challenges of scaling and upgrading to a subset of services.

# Microservice Best Practices

## Twelve-Factor App

- **Overview**: Set of best practices for building web or software-as-a-service applications.
- **Purpose**: Decouple components for cloud deployment, continuous deployment, and seamless scaling.
- **Portability**: Maximizes portability to different environments, applicable to various applications.

## Best Practices

### 1. Codebase

- **Version Control**: Track codebase in version control systems like Git.
- **Cloud Source Repositories**: Provide fully featured, private repositories.

### 2. Dependencies

- **Declaration**: Declare dependencies explicitly and store in version control.
- **Isolation**: Use language-specific tools (e.g., Maven for Java, Pip for Python) and containers.
- **Artifact Registry**: Store images and provide fine-grained access control.

### 3. Configuration

- **Environment-Specific**: Keep configuration external to the code, usually in environment variables.

### 4. Backing Services

- **Access via URLs**: Configure access to services like databases, caches, or message services via URLs.
- **Abstraction**: Swap backing services easily.

### 5. Build, Release, Run

- **Stages**: Break deployment into build, release, and run stages.
- **Artifacts**: Create identifiable artifacts for each stage.
- **Rollbacks**: Link deployment packages to specific releases for easy rollbacks.

### 6. Processes

- **Stateless**: Run applications as stateless processes.
- **State Management**: Use datastores and caches for state management.

### 7. Port Binding

- **Expose Services**: Use port numbers to expose services.
- **Deployment**: Deploy on platform services like Compute Engine, GKE, App Engine, or Cloud Run.

### 8. Concurrency

- **Scaling**: Scale out by starting new processes and scale back as needed.

### 9. Disposability

- **Reliability**: Write applications to handle infrastructure failures and restart quickly.
- **Resource Management**: Scale up and down quickly, acquiring and releasing resources as needed.

### 10. Dev/Production Parity

- **Consistency**: Use the same environments for development, test/staging, and production.
- **Tools**: Use infrastructure as code and Docker containers for consistent provisioning.

### 11. Logs

- **Decoupling**: Decouple log collection, processing, and analysis from core logic.
- **Aggregation**: Log to standard output and aggregate into a single source.
- **Google Cloud Tools**: Use tools for log collection, processing, and analysis.

### 12. Admin Processes

- **Decoupling**: Decouple one-off processes from the application.
- **Automation**: Automate and repeat processes, avoiding manual steps.
- **Google Cloud Options**: Use cron jobs in GKE, cloud tasks on App Engine, and Cloud Scheduler.

# Design of Microservices Based on REST and HTTP

## Independence of Microservices

- **Independent Deployment**: Microservices should be deployable independently.
- **Versioned Contracts**: Each microservice must provide a versioned, well-defined contract to its clients.
- **Contract Stability**: Do not break versioned contracts until no other microservice relies on them.
- **Deprecation Policies**: Account for rollback requirements in deprecation and turndown policies.
- **Organizational Challenge**: Strong, versioned contracts are crucial for stability.

## Communication and Protocols

- **HTTPS Communication**: Services communicate using HTTPS with text-based payloads (e.g., JSON, XML).
- **HTTP Methods**: Use HTTP methods like "GET" and "POST" for actions.
- **Minimal Client Knowledge**: Clients need minimal details: URI, request, and response formats.

## REST Architecture

- **Loose Coupling**: REST (Representational State Transfer) supports loose coupling.
- **Protocol Independence**: REST is protocol-independent; HTTP is common, gRPC is also used.
- **Strong Contracts**: Maintain backward compatibility and design APIs around domains, not specific use cases.

## API Design

- **Standards**: Use standards like OpenAPI for HTTP-based implementations and protocol buffers for gRPC.
- **Uniform Interfaces**: Provide consistent, uniform interfaces with consistent error reporting, URI structure, and paging.
- **Hypermedia**: Use hypermedia to provide links to additional resources, reducing client knowledge requirements.

## Resource Representation

- **URIs**: Resources are identified by URIs (endpoints).
- **Immutable Representations**: Responses return immutable representations of resource information.
- **Batch APIs**: For performance, return collections of items instead of individual items.

## Data Formats

- **Text-Based Formats**: Use JSON for public-facing APIs; XML can also be used.
- **Internal Services**: gRPC may be used for internal services, especially for performance.

## Performance and Optimization

- **Caching**: Consider caching for performance and resource optimization of immutable resources.
- **Streaming**: gRPC supports streaming, which may influence protocol choice.

## Example

- **Resource Example**: A resource could represent a dog, with representations like Noir (a Schnoodle) or Bree (a mutt).
- **Request and Response**: Making a request for a resource returns its representation, usually in JSON format.

## Best Practices

- **API Design Rules**: Implement a set of API design rules for uniform interfaces.
- **Error Reporting**: Ensure consistent error reporting across services.
- **Paging**: Use consistent paging mechanisms.
- **Caching**: Optimize performance with caching for immutable resources.

# HTTP Requests and Responses

## HTTP Requests

- **Components**: Built in three parts: request line, header variables, and request body.
- **Request Line**: Contains the HTTP verb (GET, POST, PUT, etc.), the requested URI, and the protocol version.
- **Header Variables**: Key-value pairs, including standard headers (e.g., user region) and custom headers.
- **Request Body**: Contains data to be sent to the server, relevant for commands like POST and PUT.

### Examples

1. **HTTP GET Request**

   ```json
   GET / HTTP/1.1
   Host: pets.drehnstrom.com
   ```

2. **HTTP POST Request**

   ```json
   POST /add HTTP/1.1
   Host: pets.drehnstrom.com
   Content-Type: application/json
   Content-Length: 35

   {
     "name": "Noir",
     "breed": "schnoodle"
   }
   ```

## HTTP Verbs

- **GET**: Retrieve resources.
- **POST**: Request the creation of a new resource.
- **PUT**: Create or update a resource (idempotent).
- **DELETE**: Remove a resource.

## HTTP Responses

- **Components**: Built in three parts: response line, header variables, and response body.
- **Response Line**: Contains the HTTP version and a response code.
- **Response Codes**:
  - **200s**: Success (e.g., 200 OK, 201 Created).
  - **400s**: Client errors (e.g., 403 Forbidden, 404 Not Found).
  - **500s**: Server errors (e.g., 500 Internal Server Error, 503 Service Unavailable).
- **Header Variables**: Key-value pairs indicating content type and other metadata.
- **Response Body**: Contains the resource representation in the specified format (e.g., JSON, XML, HTML).

## API Design Guidelines

- **Consistency**: Use singular nouns for individual resources and plural nouns for collections.
- **URI Structure**: Refer to resources, not actions (e.g., `/pet/1` for a specific pet, `/pets` for all pets).
- **Case Insensitivity**: URIs are case insensitive and should include version information.
- **Service Diagrams**: Diagram services to show resource access and representations.

### Example

- **URI Example**:
  - `GET /pet/1`: Fetch a pet with ID 1.
  - `GET /pets`: Fetch all pets.
- **Avoid**: URIs like `GET /getpets`.

## Best Practices

- **Diagram Services**: Visualize service interactions and resource representations.
- **Consistent Error Reporting**: Ensure uniform error reporting across services.
- **Caching**: Optimize performance with caching for immutable resources.

# API Design

## Importance of Consistent APIs

- **Consistency**: Design consistent APIs for services.
- **Google API Design Guide**: Recommendations on names, error handling, documentation, versioning, and compatibility.

## Google Cloud APIs

- **REST APIs**: Each Google Cloud service exposes a REST API.
- **Function Definition**: Form `service.collection.verb`.
  - **Service Endpoint**: Example: `compute.googleapis.com` for Compute Engine API.
  - **Collections**: Include instances, instanceGroups, instanceTemplates.
  - **Verbs**: Include LIST, GET, INSERT.
- **Example**: GET request to see all Compute Engine instances.
- **Parameters**: Passed in the URL or request body in JSON format.

## OpenAPI

- **Industry Standard**: For exposing APIs to clients.
- **Swagger**: Version 2.0 of the specification, now a set of open-source tools.
- **API-First Approach**: Design API through OpenAPI for a single source of truth.
  - **Generated Code**: Automatically generate client libraries, server stubs, and API documentation.
- **Support**: Cloud Endpoints and Apigee support OpenAPI.

## Example OpenAPI Specification

- **Petstore Service**: URI `petstore.swagger.io/v1`.
- **Endpoint**: `/pets` accessed using HTTP GET to provide a list of all pets.

## gRPC

- **Binary Protocol**: Useful for internal microservice communication.
- **Programming Languages**: Supports many languages.
- **Loose Coupling**: Via contracts defined using protocol buffers.
- **High Performance**: Based on HTTP/2, supports client and service streaming.
- **Support**: Global load balancer, Cloud Endpoints, GKE with envoy proxy.

## API Management Tools

- **Cloud Endpoints**: API management gateway for developing, deploying, and managing APIs on Google Cloud.
  - **Infrastructure**: Leverages Google's underlying infrastructure.
- **Apigee**: API management platform for enterprises.
  - **Deployment Options**: Cloud, on-premises, hybrid.
  - **Features**: API gateway, customizable portal, monetization, deep analytics.
  - **Compatibility**: Supports any HTTP/HTTPS backends.
