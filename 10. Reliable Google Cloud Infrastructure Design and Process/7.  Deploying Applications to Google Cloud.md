# Deploying Applications to Google Cloud

- Google Cloud offers many possible deployment platforms, and the choice is not always immediately obvious.
- High level overview of deciding on the most suitable platform for your application:
  - Ask yourself whether you have specific machine and OS requirements.
    - If yes, then Compute Engine is the platform of choice.
    - If no, then ask whether you are using containers.
      - If yes, consider Google Kubernetes Engine or Cloud Run, depending on whether you want to configure your own Kubernetes cluster.
      - If no, consider Cloud Functions if your service is event-driven and App Engine if it's not.
- Each of these services will be discussed in this module, with exploration in a lab.

# Compute Engine

- Compute Engine is Google Cloud's infrastructure as a service (IaaS) offering.
- Ideal for:
  - Complete control over operating systems.
  - Non-containerized applications.
  - Applications built on a microservice architecture.
  - Database applications.
- Features:
  - Instance groups and autoscaling to meet variations in demand.
  - Managed instance groups create VMs based on instance templates.
    - Instance templates define VMs and manage instance groups.
    - Templates specify boot disk image or container image, machine type, labels, and other instance properties like a startup script to install software from a Git repository.
  - Managed instance groups offer advantages:
    - Auto healing to recreate instances that don't respond.
    - Creating instances in multiple zones for high availability.
- Recommendations:
  - Use one or more instance groups as the backend for load balancers.
  - For instance groups in multiple regions, use a global load balancer.
  - Enable Cloud CDN for static content.

# Google Kubernetes Engine (GKE)

- Provides a managed environment for deploying, managing, and scaling containerized applications using Google’s infrastructure.
- Environment consists of multiple Compute Engine virtual machines grouped together to form a cluster.
- GKE clusters are powered by the Kubernetes open source cluster management system.
- Kubernetes commands and resources are used to deploy and manage applications, perform administration tasks, set policies, and monitor the health of deployed workloads.
- A cluster consists of at least one cluster control plane and multiple worker machines called nodes.
- Pods are the smallest, most basic deployable objects in Kubernetes, representing a single instance of a running process in a cluster.
- Pods contain one or more containers, such as Docker containers, that run the services being deployed.
- Optimize resource use by deploying multiple services in the same cluster.
- GKE has Autopilot and Standard modes of operation:
  - Autopilot mode: Google manages your nodes, providing a workload-focused, cost-optimized, production-ready experience.

# Cloud Run

- Deploy a container image stored in Artifact Registry to Cloud Run.
- Deploy directly from source to Cloud Run, which includes automatically creating a container image for your built source and storing the image in Artifact Registry.
- Cloud Run can automatically containerize local source code, push the container image to an Artifact Registry repository, deploy the container image to Cloud Run from the repository, and push and pull images using the repository cloud-run-source-deploy.
- If the repository does not exist, Cloud Run creates it for you if your account has the required permissions.
- Deploy a container image by tag or digest stored in Artifact Registry.
- Deploying to a service for the first time creates its first revision. Revisions are immutable.

# App Engine

- Fully managed, serverless application platform supporting the building and deploying of applications.
- Applications can be scaled seamlessly from zero upward without managing the underlying infrastructure.
- Designed for microservices.
- Each Google Cloud project can contain one App Engine application, and an application has one or more services.
- Each service can have one or more versions, and each version has one or more instances.
- Supports traffic splitting for strategies such as canary testing or A/B testing.
- Typical App Engine microservice architecture example:
  - App Engine serves as the frontend for both web and mobile clients.
  - Backend includes various Google Cloud storage solutions:
    - Cloud Storage for static content.
    - Cloud SQL for structured relational data.
    - Firestore for NoSQL storage.
    - Memcache to reduce load on datastores by caching queries.
    - Cloud Tasks for asynchronous work outside a user request.

# Cloud Functions

- Great for deploying loosely coupled, event-driven microservices.
- Designed for processing events that occur in Google Cloud.
- Functions can be triggered by changes in a Cloud Storage bucket, a Pub/Sub message, or HTTP request.
- Completely managed, scalable, and inexpensive.
- No cost if there are no requests; processing is paid for by execution time in 100ms increments.
- Example use case: Image translation service
  - Image uploaded to a Cloud Storage bucket triggers an OCR Cloud Function.
  - OCR Cloud Function identifies text in the image using Google Cloud’s Vision API.
  - Service publishes a message to a Pub/Sub topic for translation.
  - Another Cloud Function translates the identified text using the Cloud Translation API.
  - Translator Cloud Function publishes a message to a file write topic in Pub/Sub.
  - Cloud Function writes the translated image to a file.
