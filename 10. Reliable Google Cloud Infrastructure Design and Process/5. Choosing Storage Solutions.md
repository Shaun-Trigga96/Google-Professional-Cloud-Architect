- **Rich Set of Options**: Cater to different types of data, sizes, life cycles, and access patterns.

1. **Cloud Storage**: Storing binary data.
2. **Cloud SQL or Spanner**: Storing relational data.
3. **Firestore and Bigtable**: Storing NoSQL or unstructured data.

- **Memorystore**: Caching for fast data access.

# Choosing Storage Solutions

## Key Storage Characteristics

- **Google Cloud Storage Options**: Wide range of managed storage and database options.
- **Selection Criteria**: Type of data, scale, durability, availability, and location requirements.

## Storage Services

- **Relational, NoSQL, Object Storage, Data Warehouse, In-Memory**: Fully managed, scalable, backed by industry-leading SLAs.

## Availability SLAs

- **Service Configuration**: Availability SLA depends on service configuration (e.g., multi-regional, regional, coldline buckets for Cloud Storage).
- **Monthly Uptime Percentage**: Total minutes in a month minus downtime, divided by total minutes in a month.

## Durability

- **Shared Responsibility**: Google Cloud ensures data durability in hardware failure; users perform backups.
- **Cloud Storage**: 11 9’s durability, versioning feature.
- **Backups**: Recommended to turn on versioning and archive older versions; schedule snapshot jobs for disks; create on-demand backups for Cloud SQL; run export jobs for Spanner and Firestore.

## Scalability

- **Horizontal Scaling**: Adding nodes (e.g., Bigtable, Spanner).
- **Vertical Scaling**: Scaling machines (e.g., Cloud SQL, Memorystore).
- **Automatic Scaling**: No limits (e.g., Cloud Storage, BigQuery, Firestore).

## Consistency

- **Strong Consistency**: Updates all copies of data within a transaction (e.g., Cloud Storage, Cloud SQL, Spanner, Firestore).
- **Eventual Consistency**: Multiple copies of data for performance and scalability, updates asynchronously (e.g., Bigtable, Memorystore).

## Cost Considerations

- **Cost per GB**: Important for financial implications.
- **Bigtable and Spanner**: Designed for massive data sets, not cost-efficient for small datasets.
- **Firestore**: Less expensive per GB, but consider read/write costs.
- **Cloud Storage**: Suitable for certain data types, relatively inexpensive.
- **BigQuery**: Cheap storage, cost incurred for each query.

## Decision Factors

- **Type of Data**
- **Size of Data**
- **Read/Write Patterns**

# Selecting Google Cloud Storage and Data Solutions

## Google Cloud Storage and Database Portfolio

- **Relational, File, NoSQL, Object, Block, Data Warehouse, In-Memory**: Covers a wide range of storage solutions.

## Relational

- **Cloud SQL**: Fixed schema database with a storage limit of 64 TB, offered using MySQL, PostgreSQL, and SQL Server. Suitable for web applications like CMS or eCommerce.
- **Spanner**: Relational, fixed schema, scales infinitely, regional or multi-regional. Suitable for scalable relational databases >30 GB with high availability and global accessibility.
- **AlloyDB**: Fixed schema, fully managed PostgreSQL-compatible database. Provides enterprise-grade performance and availability.

## File

- **Filestore**: Schemaless, high-performance, fully managed file store service. Suitable for applications requiring a filesystem interface and shared file system for data.

## NoSQL

- **Firestore**: Completely managed document datastore with a maximum document size of 1 MB. Suitable for hierarchical data like game state or user profiles.
- **Bigtable**: NoSQL datastore that scales infinitely. Suitable for heavy read and write events, financial services, IoT, and digital advert streams.

## Object

- **Cloud Storage**: Schemaless, completely managed with infinite scale. Suitable for storing binary object data like images, media serving, and backups.

## Block

- **Persistent Disk**: Schemaless, durable network storage devices accessible like physical disks in a desktop or server. Data is distributed across several physical disks.

## Data Warehouse

- **BigQuery**: Fixed schema, supports completely managed SQL analysis of data stored. Suitable for performing analytics and business intelligence dashboards.

## In-Memory

- **Memorystore**: Schemaless-managed Redis database. Suitable for caching for web and mobile apps and providing fast access to state in microservice architectures.

## Decision Chart

1. **Is your data structured and needs to be accessed using its structured data format?**
   - **No**: Do you need a shared file system?
     - **Yes**: Choose Filestore.
     - **No**: Choose Cloud Storage.
   - **Yes**: Does your workload focus on analytics?
     - **Yes**: Choose Bigtable or BigQuery based on latency and update needs.
       - **BigQuery**: Data warehouse, optimized for large-scale, ad-hoc SQL-based analysis and reporting.
       - **Bigtable**: NoSQL wide-column database, optimized for low latency, large numbers of reads and writes, and maintaining performance at scale.
     - **No**: Is your data relational?
       - **No**: Do you need application caching?
         - **Yes**: Choose Memorystore.
         - **No**: Choose Firestore.
       - **Yes**: Do you need Hybrid transaction/analytical processing (HTAP)?
         - **Yes**: Choose AlloyDB.
         - **No**: Do you need global scalability?
           - **Yes**: Choose Spanner.
           - **No**: Choose Cloud SQL.

## Data Transfer in Google Cloud

- **Factors to Consider**: Cost, time, offline vs. online transfer options, and security.
- **Transfer Options**:
  - **Cloud Storage Transfer Service**: For smaller or scheduled data uploads.
  - **Storage Transfer Service for On-Premises Data**: For large-scale online data transfers from on-premises storage to Cloud Storage.
  - **Transfer Appliance**: For large amounts of on-premises data that would take too long to upload.
  - **BigQuery Data Transfer Service**: Automates data movement from SaaS applications to BigQuery on a scheduled, managed basis. Supports Google application sources and data connectors for easy data transfer from Teradata, Amazon Redshift, and Amazon S3.
