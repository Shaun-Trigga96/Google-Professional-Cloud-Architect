# Optimizing the Costs for Google Cloud Observability

## Costs and Pricing

- Google Cloud Observability services are managed services, so their cost is usage-based, not infrastructure-based.
- **Cloud Profiler** is offered at no cost, but **Cloud Logging**, **Cloud Monitoring**, and **Cloud Trace** have associated costs.
- **Error Reporting** supports errors sent using Cloud Logging and incurs costs associated with this service.

### Logging Pricing

- Based on the volume of chargeable logs ingested.
- Costs incurred when using:
  - Cloud Load Balancing logs
  - Custom logs
  - Error reporting costs (if errors are ingested by Cloud Logging)
  - Write operations in the Cloud Logging API
  - Logs stored beyond 30 days will incur a retention charge for non-required buckets.
- Refer to the documentation for updated pricing details.

### Cloud Monitoring Pricing

- Based on the volume of chargeable metrics ingested.
- Number of chargeable API calls.
- Execution of Cloud Monitoring uptime checks.
- Metrics ingested using Google Cloud Managed Service for Prometheus.
- Example product usage that generates cost through metric volume and API calls includes:
  - Cloud Monitoring custom metrics
  - AWS Metrics
  - Read operations in the Monitoring API, except from Google Cloud console.

### Trace Pricing

- Based on the number of spans ingested and eventually scanned.
- The free allotment was 2.5 million spans.
- Example product usage that generates cost through spans ingested includes adding instrumentation for:
  - Spans for App Engine apps outside of the default spans
  - Cloud Load Balancing
  - Custom apps

### Free Functions of Google Cloud Observability

- Using Cloud Profiler.
- Collecting and using:
  - Cloud Audit Logs
  - Access Transparency logs
  - BigQuery Data Access logs
  - Anything excluded from logs
- Creating and using dashboards.
- Visualizing Google Cloud and Anthos metrics and log streams.
- App Engine standard trace spans.
- Uptime checks.
- Logs analytics when queries are running in Cloud Logging.

### Additional Information

- After the free tier finishes, you will be charged for various operation-related fees.
- For the latest pricing information, always check the Google Documentation.
- Networking logs, including VPC Flow logs, Firewall Rules Logging, and Cloud NAT, will cost you the standard log storage fees.
  - If stored in Cloud Logging, they won't cost extra to generate.
  - If exported to an external service, costs are incurred to generate logs, in addition to any destination or networking fees.
- **Network Intelligence Center** incurs costs for:
  - Metrics overlaid on the network topology
  - Network Analyzer
  - Performance dashboard
  - Running connectivity tests
  - Firewall insights
- Refer to the documentation for more information on pricing models for Firewall insights.

# Bill Estimation

- When estimating prices in Google Cloud, use the **Google Cloud Pricing Calculator**.
  - The Pricing Calculator is accurate, but only as accurate as the data you provide.
- If your operation services are already running on Google Cloud, start by pulling the prices of what you're spending on them.
  - Look for the requisite data in several places, which we will explore in this section.
- You can also use the **Cost Estimation API**.
  - It provides customer-specific estimates that include your discounts, such as those negotiated as part of a contract and those based on committed usage.
  - These cost estimates can help you make more informed business decisions.
  - For more information, refer to the documentation linked in the reference material section.

## Steps for Bill Estimation

1. **Billing Account Reports Page**:
   - Set your date range, and then filter by Stock Keeping Unit (SKU).
   - The SKUs you want are:
     - Log volume
     - Spans ingested
     - Metric volume
     - Monitoring API Requests
   - In the chart, you can change the view to display the data.
   - When you select **Daily cumulative**, the cost trend line effectively shows where you’re headed based on current spend trends.
   - If you recently added logging, adding **Daily cumulative** might be a good way to estimate what your bill might do.
   - Check your usages and costs.
     - Note: If SKU usage is 0 for a metric, then it won’t appear in the list.
   - You can do something similar to see how money was spent in the past month.
     - In this case, the biggest item is log volume.
     - This insight might raise the question: if money is spent on logging data, where exactly is that data coming from?

2. **Metrics Explorer**:
   - Open Monitoring and then Metrics Explorer, and set the Metric to Global.
   - Depending on what you want, select one of the following:
     - **Log bytes ingested**: Provides log bytes ingested in Cloud Logging.
     - **Monthly log bytes ingested**: Provides a graph where each point represents the month-to-date sum of log bytes ingested in Cloud Logging. The monthly total is available on the last day of the month, when it also resets.
     - **Metric bytes ingested**: Provides chargeable number of bytes of metric data ingested in Cloud Monitoring.
     - **Trace spans ingested**: Provides chargeable trace spans ingested in Cloud Trace.
     - **Monthly trace spans ingested**: Provides a graph where each point represents the month-to-date sum of trace spans ingested in Cloud Trace. It resets on the last day of the month; the monthly total is found on the last day of the month.

     - Thus, the `gae_app` is where all the logging data is coming from Migrate for Compute Engine.
     - You can find more information on Migrate for Compute Engine in the documentation.

3. **Metrics Scope in Cloud Monitoring**:
   - A metrics scope is used in Cloud Monitoring to monitor the resources you care about.
   - The resources could be in a Google Cloud project, an AWS account, or multiple Google Cloud projects and AWS accounts.
   - To view your Monitoring usage by metrics scope, go to Monitoring and then Settings.
   - On the Summary tab, the **Metrics Ingested** table displays a summary of your metrics ingestion data by resource.
     - This data includes the previous month total usage, the current month to-date usage, and projected usage for the current month.
   - To get your project-level usage in detail, in the Metrics Ingested table, click **View Bill**.
     - You’re taken to the Cloud Billing Reports page.
   - After you know the projects where you’re spending on Cloud Monitoring, it should be easy to understand which metrics are driving these observability costs.
   - We also want to provide insights on how to reduce spend on unused and noisy metrics.

4. **Metrics Diagnostics**:

   - One tool is a **Metrics** table where you can sort and filter metrics by:
     - Volume or samples ingested

     - Metric labels

   - We recommend sorting metrics by **Metric Data Ingested** in descending order to identify exactly which metrics are primarily driving ingestion volume.

# Billing Best Practices

- Start with what we discussed in the previous sections:
  - Learn to calculate costs.
  - Become aware of your operations-related spend and where it goes.
  - Identify the more expensive items.

## Log Exclusions

- If you exclude log entries, you don't pay for them. However, they will be gone once excluded, so be careful with the log entries you keep.
- Common exclusions:
  - **Cloud Load Balancing**: Often, you only need a small percentage of logs. Exclude 90% or more.
  - **VPC Flow Logs**: You can often exclude more than 95% of the entries and still get enough to monitor the VPC.
  - Filter exclusions based on entry contents, e.g., retain logs from sources with a CIDR outside your network.
  - If you send VPC Flow Logs to Cloud Logging, the charges for generating VPC Flow Logs instances are waived. Only logging charges apply.
  - If you exclude VPC Flow Logs from Cloud Logging, VPC Flow Logs charges apply. To lower the bill, deactivate them completely.

### Web Applications and Services

- Exclude logging HTTP 200 OK messages from requests, as they often don't provide much insight and can generate numerous entries.

### Log Exports

- Log exports are free, but not the target resource.
- Export logs and exclude them from being ingested into Cloud Logging to reduce costs.
- Retain logs in Cloud Storage and BigQuery or use Pub/Sub to process logs while excluding them from Cloud Logging.
- Fees associated with log exports:
  - Storage fees in Cloud Storage.
  - Storage, streaming, and query fees in BigQuery.
  - Pub/Sub message and networking egress fees.
- Example: 2 TiBs of data access log data stored in Logging would cost about $1,000. The same 2 TiBs stored in a regional, standard class bucket would cost about $40. With archival, it would be much cheaper.

### Reducing Log Volumes

- Avoid sending additional logs generated by the Ops Agent to Cloud Logging in nonessential environments.
- Virtual machines continue to report standard logs to Cloud Logging but don't report logs from third-party apps or the syslog.

### Custom Metrics and Labels

- How you use labels on Monitoring custom metrics can affect the volume of time series generated.
- Example: A custom metric with two labels (cost_center and env values) can generate up to 55 time series if there are 11 cost_center values and 5 env values.
- Adding additional metric labels can significantly increase metric volume and cost.
- Limit the number of custom metric labels and select labels thoughtfully to avoid high cardinality.
- Example: Using user_id as a label results in at least one time series for each user, which can be very large with significant traffic.

### Ops Agent Metrics

- Metrics sent from the Ops Agent are chargeable.
- Weigh the advantages and disadvantages of installing the Ops Agent.
- Customize the agents through configuration files to reduce metric volumes.
- Reduce the number of VMs using the Ops Agent in nonessential environments.

### Custom Monitoring Metrics

- Custom metrics can increase spend.
- Newer metrics created using OpenTelemetry support sampling to help reduce volume.
- Reduce the number of custom monitoring metrics your apps send to reduce metric volumes.
- Open source Prometheus documentation rarely recommends filtering metric volume, but it's important when paying a managed-service provider on a unit basis.

### Reducing Metrics

- Modify scrape configs to scrape fewer targets.
- Filter exported metrics when using managed or self-deployed collection.
- Managed Service for Prometheus charges on a per-sample basis.
- Ways to reduce the number of samples ingested:
  - Increase the length of the sampling period (e.g., changing a 10-second sampling period to 30 seconds can reduce sample volume by 66%).
  - Set the scraping interval on a per-job or per-target basis.
  - For managed collection, set the scrape interval in the PodMonitoring resource using the interval field.
  - For self-deployed collection, aggregate high-cardinality metrics locally using recording rules, flags, and environment variables.

### Trace Charges

- Trace charges are based on the number of trace spans ingested and scanned.
- Use sampling to reduce the volume of traces ingested.
- Sampling provides insight into the breakdown of latency caused by app components, such as RPC calls.
- Example: For a popular web application with 5000 queries/second, sampling 5% of app traffic instead of 20% can reduce the number of spans ingested into Trace to one-fourth.
- OpenTelemetry lets you specify a sampling rate.
- Enforce span quotas with the API-specific quota page in the Google Cloud console.
- Setting a quota lower than the default product quota ensures your project won't exceed the specific quota limit.
- Quotas help ensure that your costs are expected.
- Understand how instrumented apps interact to assess the effect of the number of spans ingested.
