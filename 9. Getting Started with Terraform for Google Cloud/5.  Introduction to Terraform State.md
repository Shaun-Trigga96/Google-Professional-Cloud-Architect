# Introduction to Terraform State

## What is Terraform State?

- **Metadata Repository**: Stores metadata for your infrastructure configuration.
- **State File**: Saves the state of the resources managed by Terraform.
  - Default location: `terraform.tfstate` (stored locally).
  - Recommended for team environments: Store state remotely.

### Purpose of Terraform State

- **Track Configuration**: Keeps track of your infrastructure configuration.
- **Create Plans and Changes**: Uses the local state to create plans and change your infrastructure.
- **Refresh State**: Updates the state with the real infrastructure before any operation.

### How Terraform State Works

- **Store Bindings**: Stores bindings between objects in a remote system and resource instances declared in your configuration.
- **Record Identity**: Records the identity of remote objects against particular resource instances when created.
- **Update or Delete**: Potentially updates or deletes objects in response to future configuration changes.

### State File Operations

- **First-Time Application**: Creates infrastructure resources and generates a state file with references to resource names.
- **Comparison**: Compares configuration with the state file and current live state to generate a plan.
- **Apply Plan**: Updates resources to match the defined configuration and updates the state file.
- **In-Place Updates**: If arguments cannot be updated in-place due to remote API limitations, the resource is destroyed and re-created.
- **Resource Removal**: If a resource is removed from the configuration but exists in the state file, Terraform destroys the resource.

# State File Storage

## Local State Files

- **Default Storage**: Terraform saves local state files in the current working directory with a `.tfstate` extension.
- **Single Developer**: Local states work well when there’s only one developer working on a project.
- **Challenges in Team Environments**:
  - **No Shared Access**: Each team member needs access to the same state files, requiring shared storage.
  - **No Locking**: Multiple developers running Terraform simultaneously can encounter race conditions, leading to conflicts, data loss, and state file corruption.
  - **Lack of Confidentiality**: Local state files are in plain text, exposing sensitive data.

### Remote State File Storage

- **Automatic Updates**: The state file is automatically updated when stored remotely.
  - Terraform loads the state file from the backend every time you run the plan or apply commands.
  - The state file is stored in the backend after each apply, reducing manual errors.
- **State Locking**: Remote Cloud Storage buckets support state locking to prevent corruption from simultaneous updates.
- **Enhanced Security**: Remote storage is more secure with encryption in transit and on disk.
  - **Access Permissions**: Configure access permissions using IAM policies.
  - **Additional Encryption**: Use customer-supplied encryption keys and the `GOOGLE_ENCRYPTION_KEY` environment variable for extra protection.

### Storing Terraform State in a Cloud Storage Bucket

1. **Add `google_storage_bucket` Resource**:
    - Add the following code to `main.tf`:

      ```hcl
      resource "google_storage_bucket" "state_bucket" {
        name     = "my-terraform-state-bucket"
        location = "US"
      }
      ```

    - Run `terraform apply` to create the storage bucket.

2. **Configure Backend**:
    - Add the following code to `backend.tf`:

      ```hcl
      terraform {
        backend "gcs" {
          bucket = "my-terraform-state-bucket"
        }
      }
      ```

    - Run `terraform init` to configure the Terraform backend.
    - Terraform will prompt you to copy the local state file to the new Cloud Storage bucket. Enter `yes`.

3. **State Management**:
    - After running `terraform init`, Terraform state is stored in the Cloud Storage bucket.
    - Terraform pulls the latest state from the bucket before running a command and pushes the latest state to the bucket after running it.

### Example State File Snippet

- The state file includes metadata of the resources created, such as the resource type, resource name, and provider name.

## Best Practices for Terraform State Optimization and Security

### Remote State for Team Environments

- **Use Remote State**: Store state files remotely to enable state locking and versioning.
- **Google Cloud Storage**: Use Cloud Storage state backend to lock the state, separate sensitive information from version control, and restrict access to the remote state bucket to the build system and highly privileged administrators.

### Source Control

- **Use `.gitignore`**: Prevent accidentally committing development state to source control by adding Terraform state files to `.gitignore`.

### Handling Secrets

- **Avoid Storing Secrets**: Do not store secrets in the state file, as many resource and data providers store secret values in plain text.
- **Encrypt State File**: Always encrypt the state file to add an extra layer of defense.
  - **Customer-Supplied Encryption Keys**: Use customer-supplied encryption keys for added protection, even though Cloud Storage buckets are encrypted at rest.

### State File Integrity

- **Do Not Modify Manually**: Avoid manual modifications to the Terraform state file.
  - **Importance**: The state file is critical for maintaining the mapping between the Terraform configuration and Google Cloud resources.
  - **Risk**: Manual modifications can lead to corruption and major infrastructure problems.

# Creating a Remote Backend

## Overview
In this lab, you will create a local backend and then create a Cloud Storage bucket to migrate the state to a remote backend.

## Objectives
In this lab, you will learn how to perform the following tasks:

- Create a local backend.
- Create a Cloud Storage backend.
- Refresh your Terraform state.

## Task 2: Verify Terraform is Installed

1. **Activate Cloud Shell**:
   - On the Google Cloud menu, click **Activate Cloud Shell**.
   - If prompted, click **Continue**.

2. **Confirm Terraform Installation**:

   ```sh
   terraform --version
   ```

## Task 3: Add a Local Backend

1. **Create `main.tf` Configuration File**:
   - In a new Cloud Shell window, create `main.tf`:

     ```sh
     touch main.tf
     ```

2. **Retrieve Project ID**:

   ```sh
   gcloud config list --format 'value(core.project)'
   ```

3. **Open Cloud Shell Editor**:
   - On the Cloud Shell toolbar, click **Open Editor**.
   - Switch between Cloud Shell and the code editor as required.

4. **Add Cloud Storage Bucket Resource Code to `main.tf`**:

   ```hcl
   provider "google" {
     project = "Project ID"
     region  = "Region"
   }

   resource "google_storage_bucket" "test-bucket-for-state" {
     name                        = "Project ID"
     location                    = "US" # Replace with EU for Europe region
     uniform_bucket_level_access = true
   }

   terraform {
     backend "local" {
       path = "terraform/state/terraform.tfstate"
     }
   }
   ```

5. **Initialize Terraform**:
   - On the Cloud Shell toolbar, click **Open Terminal**, then initialize Terraform:

     ```sh
     terraform init
     ```

6. **Apply Changes**:

   ```sh
   terraform apply
   ```

   - Type `yes` at the prompt to confirm.

7. **Examine State File**:

   ```sh
   terraform show
   ```

## Task 4: Add a Cloud Storage Backend

1. **Replace Local Backend with GCS Backend in `main.tf`**:

   ```hcl
   terraform {
     backend "gcs" {
       bucket = "Project ID"
       prefix = "terraform/state"
     }
   }
   ```

2. **Initialize Backend Again**:

   ```sh
   terraform init -migrate-state
   ```

   - Type `yes` at the prompt to confirm.

3. **Verify State File in Cloud Storage Bucket**:
   - In the Cloud Console, navigate to **Cloud Storage > Bucket**.
   - Click on your bucket and navigate to the file `terraform/state/default.tfstate`.

## Task 5: Refresh the State

1. **Add Label to Storage Bucket**:
   - In the Cloud Console, select the checkbox next to the bucket name, and click the **Labels** button.
   - Click **+ADD LABEL**, set `Key1 = key` and `Value1 = value`, then click **Save**.

2. **Update State File**:

   ```sh
   terraform refresh
   ```

## Task 6: Clean Up the Workspace

1. **Revert Backend to Local in `main.tf`**:

   ```hcl
   terraform {
     backend "local" {
       path = "terraform/state/terraform.tfstate"
     }
   }
   ```

2. **Initialize Local Backend Again**:

    ```sh
    terraform init -migrate-state
    ```

    - Type `yes` at the prompt to confirm.

3. **Add `force_destroy` Argument to Bucket Resource in `main.tf`**:

    ```hcl
    resource "google_storage_bucket" "test-bucket-for-state" {
      name                        = "Project ID"
      location                    = "US" # Replace with EU for Europe region
      uniform_bucket_level_access = true
      force_destroy               = true
    }
    ```

4. **Apply Changes**:

    ```sh
    terraform apply
    ```

    - Type `yes` at the prompt to confirm.

5. **Destroy Infrastructure**:

    ```sh
    terraform destroy
    ```

    - Type `yes` at the prompt to confirm.
