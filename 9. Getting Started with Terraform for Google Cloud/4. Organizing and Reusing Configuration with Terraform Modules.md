# Introduction to Terraform Modules

## Why Modules are Necessary

- **Scenario**: Creating a web server in a custom network.
  - Typical attributes: machine type, disk, static IP address, Google service account.
- **Challenges**:
  - Deploying several servers of the same kind requires manual code copying.
  - Updating attributes across multiple servers is cumbersome and error-prone.
  - Code becomes unmanageable and harder to read as it grows.
  - Duplicated blocks can cause discrepancies when updated.

### DRY Principle

- **DRY (Don't Repeat Yourself)**: Avoid repeating the same set of code multiple times.
- **Abstraction**: Replace repeated code with abstraction to avoid redundancy.
- **Benefits**: Encourages building efficient, readable, and reusable code.

### Terraform Modules

- **Purpose**: Implement the DRY principle by placing reusable code inside a module.
- **Definition**: A group of one or more Terraform configuration files in a directory.
- **Usage**: Group a set of resources together and reuse them later.
- **Root Module**: The directory from which you run Terraform commands, consisting of `.tf` files stored in your working directory.

### Creating Modules

1. **Create Directories**: Create directories named `network` and `server`.
2. **Add `main.tf` Files**: Each directory has its own `main.tf` file.
   - **Network Module**: Contains networking resources to host the server.
   - **Server Module**: Contains necessary compute resources that define the server.

### Example

- **Network Module**:

  ```hcl
  # network/main.tf
  resource "google_compute_network" "custom_network" {
    name = "custom-network"
  }
  ```

- **Server Module**:

  ```hcl
  # server/main.tf
  resource "google_compute_instance" "web_server" {
    name         = "web-server"
    machine_type = "e2-medium"
    boot_disk {
      initialize_params {
        image = "debian-cloud/debian-11"
      }
    }
    network_interface {
      network = "custom-network"
      access_config {}
    }
  }
  ```

### Instantiating Modules

- **Instantiation**: Modules are instantiated when called with the `terraform apply` command.

# Where and How Modules Can Be Useful

## Managing Infrastructure as Code

- **Challenge**: Managing your entire cloud environment with a single Terraform configuration file can make the code unreadable and unmanageable as your business scales.
- **Solution**: Break your code into reusable modules to enhance readability and manageability.

### Eliminating Repetition

- **Repetition Issue**: Repeated sets of resources make the code longer and harder to read.
- **Standardization**: Place code in a module to standardize the configuration.
  - Example: Deploying database servers with encrypted disks by hardcoding the encryption configuration in a module.

### Benefits of Using Modules

1. **Enhanced Readability**: Modules eliminate redundant lines of code by calling the source module.
2. **Reusability**: Write code once and reuse it multiple times across various environments.
3. **Abstraction**: Separate configurations into logical units, reducing dependencies and making them easier to debug.
4. **Consistent Resource Replication**: Package sets of resource configurations for consistent replication.

### Practical Example

- **Database Servers with Encrypted Disks**:
  - Ensure encryption by hardcoding the encryption configuration in a module.
  - Call the module whenever a disk needs to be created.

# Calling Modules from the Parent `main.tf` File

- **Calling a Module**: Reuse a module in your configuration by referencing the code in the module block.
- **Example**: `main.tf` is the calling module.

## Using the `source` Argument

- **Purpose**: Determines the location of the module source code.
- **Requirement**: Every module call within Terraform requires a mandatory `source` argument, a meta-argument within the module block.
- **Types of Source Paths**:
  - Local path within the root directory.
  - Remote path to a module source that Terraform downloads.

### Supported Source Types

- **Terraform Registry**
- **GitHub**
- **Bitbucket**
- **HTTP URLs**
- **Cloud Storage Buckets**

### Local Path

- **Usage**: Reference a module stored within the same directory as the calling module.
- **Example**:

  ```hcl
  module "servers" {
    source = "./servers"
  }
  ```

- **Characteristics**: Local paths start with `./` or `../`. They do not require any installation as files are locally referenced from the child module to the parent module directly.

### Terraform Registry

- **Purpose**: Contains a directory of publicly available modules for various infrastructure components (e.g., load balancers, SQL instances).
- **Format**: `terraform-google-modules/gcloud/google`
- **Version Constraint**: Recommended to use version constraints to avoid unwanted changes.
  - **Example**:

    ```hcl
    module "gcloud" {
      source  = "terraform-google-modules/gcloud/google"
      version = "3.0.0"
    }
    ```

### GitHub Repository

- **Usage**: Enter the GitHub URL where the source code is located.
- **Example**:

  ```hcl
  module "example" {
    source = "github.com/username/repo"
  }
  ```

### Initializing Modules

- **Command**: Run `terraform init` to download any modules referenced by a configuration.

# Using Variables and Outputs in Modules

## Parameterizing Modules with Variables

- **Hardcoded Attributes**: Hardcoding resource attributes can lead to name conflict errors when reusing modules.
- **Flexibility**: Use variables to configure attributes differently in different environments (e.g., development, production, staging).

### Example: Parameterizing the Name Argument

1. **Replace Hardcoded Values**: Replace hardcoded values within your module with a variable.
   - Example: Replace network name with `var.network_name`.
2. **Declare Variables**: Declare the attributes that are parameterized in the `variables.tf` file.
   - Place the declared variables in the same directory as the defined resource.
   - Specify the appropriate variable type.
3. **Pass Values to Variables**: Pass the value to the input variable when calling the module.
   - Example: Reuse the same network module twice with different names.

### Example Code

- **Network Module (`network/main.tf`)**:

  ```hcl
  resource "google_compute_network" "custom_network" {
    name = var.network_name
  }
  ```

- **Variables (`network/variables.tf`)**:

  ```hcl
  variable "network_name" {
    type        = string
    description = "Name of the network"
  }
  ```

- **Calling Module (`main.tf`)**:

  ```hcl
  module "my_network_1" {
    source       = "./network"
    network_name = "network-1"
  }

  module "my_network_2" {
    source       = "./network"
    network_name = "network-2"
  }
  ```

### Using Outputs to Pass Resource Attributes

- **Purpose**: Pass resource arguments from one module to another using output values.
- **Example**: Pass the network name from the network module to the server module.

### Example Code

- **Output Value in Network Module (`network/outputs.tf`)**:

  ```hcl
  output "network_name" {
    value       = google_compute_network.custom_network.name
    description = "The name of the network"
  }
  ```

- **Variable in Server Module (`server/variables.tf`)**:

  ```hcl
  variable "network_name" {
    type        = string
    description = "Name of the network"
  }
  ```

- **Server Module (`server/main.tf`)**:

  ```hcl
  resource "google_compute_instance" "web_server" {
    name         = "web-server"
    machine_type = "e2-medium"
    boot_disk {
      initialize_params {
        image = "debian-cloud/debian-11"
      }
    }
    network_interface {
      network = var.network_name
      access_config {}
    }
  }
  ```

- **Calling Module (`main.tf`)**:

  ```hcl
  module "my_network_1" {
    source       = "./network"
    network_name = "network-1"
  }

  module "my_server" {
    source       = "./server"
    network_name = module.my_network_1.network_name
  }
  ```

### Initializing Modules

- **Command**: Run `terraform init` to download any modules referenced in a configuration.

# Best Practices for Using Modules

## General Guidelines

- **Avoid Over-Using Modules**: Modularize your code to keep it DRY, but don't fixate on eliminating all duplications.
  - Duplication can allow for more explicit configuration and easier visualization of infrastructure.

- **Use Terraform Features**: For looping over multiple values, use Terraform features such as `count` or `for_each` instead of custom scripting.

### Intelligent Parameterization

- **Parameterize Sensibly**: Only parameterize modules if it makes sense for end users to change the values.
  - Example: In a custom network module, standardize `MTU` and `routing_mode`, but parameterize the network name for reusability.

- **Focus on Changeable Values**: Parameterize values that must change; hardcoding is acceptable for fixed values.

### Organizing Code

- **Use Local Modules**: Organize and encapsulate your code using local modules from the beginning to reduce maintenance burden as infrastructure grows in complexity.

### Utilizing Public Modules

- **Terraform Registry**: Use the public Terraform Registry to find modules and implement your configuration quickly and confidently.

### Sharing Modules

- **Publish and Share**: Share modules with your team to create and maintain infrastructure.
  - Modules can be published either publicly or privately.

### Scenario: Managing Complex Infrastructure

- **Application Development Environment**:
  - New features or modifications are approved by passing code from development to staging, and then to production.
  - Each environment has the same type of resources but differs in quantity.

- **Directory Structure**: Assume directories for development, staging, and production.

- **Without Modules**: Code is manually copied to staging and production after approval and testing.

- **With Modules**: Define reusable code within a module (e.g., `server`).
  - Changes to the module are reflected across all environments.
  - Reference the module in development, staging, and production environments with different names and server quantities.
