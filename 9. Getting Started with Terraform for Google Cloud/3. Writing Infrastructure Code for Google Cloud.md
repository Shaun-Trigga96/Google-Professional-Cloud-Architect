# Resources

## Introduction to Resources

- **Resources** are infrastructure elements, such as Compute Engine instances and Cloud Storage buckets.
- Configured with Terraform code.
- Real-world infrastructure has diverse resources and resource types.
- Terraform uses Google Cloud service APIs to deploy resources.

### Types of Resources

- Instances, instance templates, groups, VPC networks, firewall rules, VPN tunnels, Cloud Routers, load balancers.

### Defining Resources

- Resources are defined within a `.tf` file.
- Recommended to place similar types of resources in a directory and define them in the `main.tf` file.
- `main.tf` is the root configuration.

### Resource Block

- Used to declare a single infrastructure object.
- **Resource type** identifies the type of resource being created, depending on the provider declared within a Terraform module.
- **Provider** is a plugin providing a collection of resource types (e.g., Google Cloud).

### Resource Arguments

- Use expressions to declare attributes.
- Some arguments are mandatory, others are optional.
- Attributes define advanced features associated with a resource.

### Multiple Resources

- Multiple resources of the same or different types can be included within the same Terraform configuration file.
- Resources can span across multiple providers.

### Example Resource Blocks

- **VPC Network**: `google_compute_network` with required `name` argument.
- **VPC Subnet**: `subnetwork-ipv6` with required `name`, `network`, and `IP CIDR range` arguments.

### Accessing Resource Attributes

- Use the format `google_compute_network.vpc_network.id` to access attributes from another resource block.
- This method is used when resources are defined within the same root configuration.

### Important Factors

- A declared resource is identified by its type and name.
- Resource name must be unique within the module.
- Resource type is a keyword associated with the provider and cannot be user-defined.
- All configuration arguments must be enclosed within the resource block body (curly brackets).
- A Terraform configuration must have all required arguments defined to pass the plan and apply phases successfully.

# Resource Meta-Arguments

## Introduction to Meta-Arguments

- Terraform language defines several meta-arguments to change the behavior of resources.
- Meta-arguments can be used with any resource type.

### Key Meta-Arguments

1. **count**
   - Creates multiple instances based on the defined value.
   - Example: Deploying multiple VM instances with a single resource block using `count`.

2. **for_each**
   - Creates multiple instances according to a map or set of strings.
   - Example: Assigning specific values to instances in different zones using `for_each`.

3. **depends_on**
   - Specifies explicit dependencies between resources.

4. **lifecycle**
   - Defines the lifecycle of a resource.
   - Prevents destruction of a resource for compliance purposes.
   - Creates a resource before destroying the replaced resource (used for high availability).

5. **provider**
   - Selects a non-default provider configuration.
   - Allows multiple configurations for a provider, including default.

### Detailed Examples

- **count Meta-Argument**
  - Reduces redundant code by creating multiple instances.
  - `count.index` represents the index number of the current count loop.
  - Example: Naming instances `dev_VM1`, `dev_VM2`, and `dev_VM3` using `count`.

- **for_each Meta-Argument**
  - Suitable when instances need distinct values that can't be derived from an integer.
  - Can be assigned to a string of values or a map.
  - Example: Creating instances in specific zones with names prefixed by zones using `for_each`.

### Practical Application

- Use `count` for almost identical instances.
- Use `for_each` for instances requiring distinct values.

# Resource Dependencies

## Visual Representation

- **Dependency Graph**: Helps understand infrastructure connections and interdependencies before deployment.
- Terraform builds a dependency graph from configurations to generate plans and refresh state.
- Attributes are interpolated during runtime, connecting variables, output values, and providers in a dependency tree.

### Types of Dependencies

1. **Implicit Dependencies**
   - Known to Terraform.
   - Example: A compute instance cannot be created without a network.

2. **Explicit Dependencies**
   - Unknown to Terraform and must be explicitly mentioned.
   - Example: Using `depends_on` to declare that a Cloud Storage bucket must be created before an application runs.

### Handling Dependencies

- **Implicit Dependencies**
  - Created through interpolation expressions.
  - Example: Reference to `my_network` in the `network` argument creates an implicit dependency on the `google_compute_network` block.

- **Explicit Dependencies**
  - Defined with the `depends_on` argument within the dependent resource block.
  - Provides flexibility to control the order of resource processing.
  - Example: Creating a client VM only after the server VM is successfully created using `depends_on`.

### Practical Examples

- **Implicit Dependency Example**
  - Compute instance `my_instance` created in a custom VPC `my_network`.
  - Terraform infers the dependency and creates the network before the instance.

- **Explicit Dependency Example**
  - Two VMs: server and client.
  - Client VM created only after the server VM using `depends_on`.

### Configuration Organization

- The order of resource definitions does not affect how Terraform applies changes.
- Organize configuration files in a way that makes sense for your team.

### Execution

- Upon executing `terraform apply`, Terraform processes the resources in the specified order, respecting both implicit and explicit dependencies.

# Variables

## Introduction to Variables

- **Purpose**: Parameterize configuration and define argument values during the apply phase.
- **Benefits**: Standardize code while maintaining flexibility to customize resource attributes at runtime.

### Input Variables

- Serve as parameters for Terraform, allowing easy customization and sharing without altering source code.
- Ways to set values at runtime: environment variables, CLI options, key-value files.

### Declaring Variables

- **Variable Block**: Variables must be declared in the variable block.
- **Best Practice**: Save all variable declarations in a separate file named `variables.tf`.
- **Naming Rules**:
  1. Name must be unique within a module.
  2. Names cannot be keywords.

### Variable Types

- **Primitive Types**:
  - `bool`: Binary values (true or false).
  - `number`: Numeric variables.
  - `string`: Sequence of Unicode characters.

### Meta Arguments

- **default**: Assigns a default value to an attribute.
- **description**: Documents the purpose of the variable, displayed during the apply phase if the variable doesn't have a defined value.
- **sensitive**: Protects sensitive information from being displayed in command outputs or log files.

### Accessing Variable Values

- Use the expression `var.<variable_name>` to access the value of a variable declared within the module.
- Example: `var.bucket_storage_class` in the resource block.

### Setting Variable Values at Runtime

- **Environment Variables**: Useful in scripts and pipelines.
- **CLI Options**: Useful for running quick examples on simple files.
- **Key-Value Files**: Use `.tfvars` or `.tfvars.json` files to quickly switch between and version sets of variables.

### Overriding Variable Values

- **Order of Precedence**:
  1. `-var` option (highest precedence).
  2. `.tfvars` file.
  3. Environment variables.
  4. Default value in the variable block.

### CLI Prompt

- If a required variable has not been set using a described method, Terraform prompts you on the CLI during the plan phase.

### Validation

- **Validation Block**: Includes a condition argument for validation rules.
- Example: `contains` condition to validate that the storage class value is uppercase and an accepted value.

### Practical Examples

- **Sensitive Variables**: Marking variables as sensitive to protect confidential information.
- **Variable Files**: Using `.tfvars` files to manage variable definitions.

### Example: Defining and Using Variables in Terraform

Let's say you want to create a Google Cloud Storage bucket with customizable attributes such as the name, location, and storage class. You can use variables to parameterize these values.

#### Step 1: Declare Variables

First, declare the variables in a `variables.tf` file:

```hcl
# variables.tf

variable "bucket_name" {
  description = "The name of the storage bucket"
  type        = string
  default     = "my-default-bucket"
}

variable "bucket_location" {
  description = "The location of the storage bucket"
  type        = string
  default     = "US"
}

variable "bucket_storage_class" {
  description = "The storage class of the bucket"
  type        = string
  default     = "STANDARD"
}

variable "sensitive_info" {
  description = "Sensitive information"
  type        = string
  sensitive   = true
}
```

#### Step 2: Use Variables in Resource Block

Next, use these variables in your `main.tf` file to define the Google Cloud Storage bucket:

```hcl
# main.tf

provider "google" {
  project = "my-gcp-project"
  region  = "us-central1"
}

resource "google_storage_bucket" "my_bucket" {
  name          = var.bucket_name
  location      = var.bucket_location
  storage_class = var.bucket_storage_class
}

resource "google_storage_bucket_object" "sensitive_object" {
  name   = "sensitive.txt"
  bucket = google_storage_bucket.my_bucket.name
  content = var.sensitive_info
}
```

#### Step 3: Set Variable Values at Runtime

You can set the variable values at runtime using a `.tfvars` file, environment variables, or CLI options. Here's an example of a `.tfvars` file:

```hcl
# terraform.tfvars

bucket_name         = "my-custom-bucket"
bucket_location     = "EU"
bucket_storage_class = "NEARLINE"
sensitive_info      = "my-secret-password"
```

Alternatively, you can set the values using CLI options:

```sh
terraform apply -var="bucket_name=my-custom-bucket" -var="bucket_location=EU" -var="bucket_storage_class=NEARLINE" -var="sensitive_info=my-secret-password"
```

### Summary

- **Variables Declaration**: Declared in `variables.tf` with descriptions, types, and default values.
- **Resource Block**: Uses `var.<variable_name>` to reference variable values.
- **Setting Values**: Can be done via `.tfvars` files, environment variables, or CLI options.

# Best Practices for Using Variables

## Parameterizing Values

- **Only parameterize values that vary for each instance or environment.**
- Ensure a concrete use case for changing a variable before exposing it.
- Avoid exposing variables with a small chance of being needed.

### Compatibility

- **Backward Compatibility**: Changing or adding a variable with a default value is backward-compatible; removing a variable is not.

### Providing Values

- **Root Modules**: Provide values to variables using a `.tfvars` file.
- Avoid alternating between var-files and command-line options.
  - Command-line options are ephemeral, easy to forget, and cannot be checked into source control.
  - Default variable files are more predictable.

### Naming Conventions

- **Descriptive Names**: Give variables names that are relevant to their usage or purpose.
- **Units in Names**: Variables representing numeric values (e.g., disk sizes, RAM size) should include units in their names.
  - Example: `disk_size_gb`, `ram_size_mb`.
  - Clears the expected input unit for configuration maintainers.

### Boolean Variables

- **Positive Names**: Give boolean variables positive names to simplify conditional logic.
  - Example: `enable_external_access`.

### Descriptions

- **Include Descriptions**: Variables must have descriptions.
  - Descriptions are included in documentation and provide additional context for new developers.

# Output Values

## Introduction to Output Values

- **Purpose**: Similar to return values in programming languages.
- **Usage**: View information about created infrastructure resources on the command line.

### Common Use Cases

- **Print Resource Attributes**: Display root module resource attributes in the CLI after deployment.
- **Pass Information**: Transfer information from one resource to another (e.g., IP addresses).

### Declaring Output Values

- **Output Block**: Use the `output` block to declare output values.
- **Best Practice**: Declare output values in a separate file named `output.tf`.

### Output Block Arguments

1. **value** (required): Returns a value to the user of the module.
2. **description** (optional): Provides an explanation of the output's purpose and expected value.
3. **sensitive** (optional): Masks the value to hide confidential information (e.g., passwords).

### Example

- **Output Value Declaration**:

  ```hcl
  output "object_url" {
    value       = google_storage_bucket_object.picture.url
    description = "The URL of the uploaded object"
    sensitive   = false
  }
  ```

### Best Practices for Output Values

- **Output Useful Information**: Only output computed information.
- **Avoid Redundant Outputs**: Do not output values that simply repeat variables or known information.
- **Meaningful Names and Descriptions**: Provide clear names and descriptions for outputs.
- **Organize Outputs**: Include all output values in a file named `output.tf`.
- **Mark Sensitive Outputs**: Use the `sensitive` argument to protect confidential information.

### Practical Example

- **Useful Computed Attributes for a Network Resource**:
  - `id`: Identifier for the resource.
  - `gateway_ipv4`: Gateway address for default routing out of the network.
  - `self_link`: URI of the created resource.

### Querying Output Values

- **Command**: Use `terraform output` to query all output values in a project.

## Task 4: Create Explicit Dependency

Explicit dependencies are used to inform dependencies between resources that are not visible to Terraform. In this example, you will run an instance that expects to use a specific Cloud Storage bucket, but that dependency is configured inside the application code and thus not visible to Terraform. You can use `depends_on` to explicitly declare the dependency.

1. **Create `exp.tf` File**:
    - Right-click on `tfinfra` folder and click **New File**.
    - Name the new file `exp.tf`, and then click **OK**.
    - Add the following base code into `exp.tf`:

      ```hcl
      # Create a new instance that uses the bucket
      resource "google_compute_instance" "another_instance" {
        name         = "terraform-instance-2"
        machine_type = "e2-micro"
        boot_disk {
          initialize_params {
            image = "debian-cloud/debian-11"
          }
        }
        network_interface {
          network = "default"
          access_config {}
        }
        # Tells Terraform that this VM instance must be created only after the
        # storage bucket has been created.
        depends_on = [google_storage_bucket.example_bucket]
      }

      # New resource for the storage bucket our application will use.
      resource "google_storage_bucket" "example_bucket" {
        name     = "<UNIQUE-BUCKET-NAME>"
        location = "US"
        website {
          main_page_suffix = "index.html"
          not_found_page   = "404.html"
        }
      }
      ```

    - Note: Replace `<UNIQUE-BUCKET-NAME>` with a unique, valid name for the bucket.
    - Save the file.

2. **Preview Resources**:

    ```sh
    terraform plan
    ```

    If prompted, enter the details for the instance creation:

    ```sh
    var.instance_name: myinstance
    var.instance_zone: ZONE
    ```

3. **Apply Terraform Configuration**:

    ```sh
    terraform apply
    ```

    If prompted, enter the details for the instance creation:

    ```sh
    var.instance_name: myinstance
    var.instance_zone: ZONE
    ```

    Confirm the planned actions by typing `yes`.

    Observe that due to the explicit dependency, the compute instance is created after the creation of the Cloud Storage Bucket.

    ```sh
    google_storage_bucket.example_bucket: Creating...
    google_storage_bucket.example_bucket: Creation complete after 1s [id=qwiklabs-gcp-03-4662a5b49176-abc]
    google_compute_instance.another_instance: Creating...
    google_compute_instance.another_instance: Still creating... [10s elapsed]
    google_compute_instance.another_instance: Creation complete after 14s [id=projects/qwiklabs-gcp-03-4662a5b49176/zones/ZONE/instances/terraform-instance-2]
    ```
