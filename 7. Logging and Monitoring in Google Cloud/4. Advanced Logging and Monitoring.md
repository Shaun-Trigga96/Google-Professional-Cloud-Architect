
# Advanced Cloud Logging and Monitoring

## Overview

Cloud Logging allows you to store, search, analyze, monitor, and alert on log data and events from Google Cloud. It is a fully managed service that performs at scale and can ingest application and system log data from thousands of VMs.

## Importance

- Logs are one of the top most visited sections in Google Cloud console.
- Logs are crucial for troubleshooting and information gathering without overwhelming the user.
- Logs are the pulse of your workloads and applications.

## Benefits of Cloud Logging

- **Data Gathering**: Collects data from various workloads to troubleshoot and understand application needs.
- **Data Analysis**: Tools like Error Reporting, Log Explorer, and Log Analytics help focus on large data sets.
- **Log Routing**: Route logs to specific regions or services for compliance or business benefits.
- **Compliance Insights**: Leverage audit and app logs for compliance patterns and issues.

## Cloud Logging Architecture

### Components

1. **Log Collection**:
   - Sources: Google Cloud services (Compute Engine, App Engine, Kubernetes Engine) or your own applications.
2. **Log Routing**:
   - Uses inclusion and exclusion filters to route log data to destinations.
3. **Log Sinks**:
   - **Cloud Logging log buckets**: Designed for storing log data.
   - **Cloud Pub/Sub topics**: Route log data to other services.
   - **BigQuery**: Petabyte-scale analytics data warehouse for storing and analyzing log data.
   - **Cloud Storage buckets**: Store log data as JSON files.

### Log Analysis Tools

- **Logs Explorer**: Optimized for troubleshooting with features like log streaming.
- **Error Reporting**: Automated error grouping and notifications for critical application errors.
- **Logs-based Metrics**: Dashboards and alerting to make logs actionable.
- **Log Analytics**: Ad hoc log analysis capabilities.

## Conclusion

Cloud Logging is an essential tool for managing and analyzing log data, providing insights and ensuring compliance across various workloads and applications.

The Log Router is responsible for routing log data to its destination. It uses a combination of inclusion filters and exclusion filters to determine which log data is routed to each destination.

## Log Storage

Log sinks are destinations where log data is stored. Cloud Logging supports a variety of log sinks, including:

- **Cloud Logging log buckets**: Designed for storing log data.
- **Cloud Pub/Sub topics**: Used to route log data to other services, such as third-party logging solutions.
- **BigQuery**: A fully-managed, petabyte-scale analytics data warehouse for storing and analyzing log data.
- **Cloud Storage buckets**: Provide storage of log data in Cloud Storage, with log entries stored as JSON files.

## Log Visualization

Cloud Logging provides several tools to analyze logs:

- **Logs Explorer**: Optimized for troubleshooting use cases with features like log streaming.
- **Error Reporting**: Helps users react to critical application errors through automated error grouping and notifications.
- **Logs-based Metrics**: Dashboards and alerting provide ways to understand and make logs actionable.
- **Log Analytics**: Expands the toolset to include ad hoc log analysis capabilities.

## Log Routing and Exporting

Cloud Logging is a collection of components exposed through a centralized logging API. The components include log router, log sinks, and log storage.

### Log Router

- Entries are passed through the API and fed to the Log Router.
- Optimized for processing streaming data, reliably buffering it, and sending it to any combination of log storage and sink (export) locations.
- By default, log entries are fed into one of the default logs storage buckets.
- Exclusion filters can be created to partially or totally prevent this behavior.
- Log sinks run in parallel with the default log flow and can direct entries to external locations such as additional Cloud Logging buckets, Cloud Storage, BigQuery, Pub/Sub, or external projects.
- Inclusion and exclusion filters control which logging entries end up at a particular destination and which are ignored completely.

### Log Sinks

For each Google Cloud project, Logging automatically creates two logs buckets: _Required and_Default, and corresponding log sinks with the same names.

- **_Required**:
  - Holds Admin Activity audit logs, System Event audit logs, and Access Transparency logs.
  - Retains logs for 400 days.
  - No charge for logs stored here, and the retention period cannot be modified.
  - Cannot be deleted or modified.
- **_Default**:
  - Holds all other ingested logs in a Google Cloud project, except for the logs held in the _Required bucket.
  - Standard Cloud Logging pricing applies.
  - Logs are retained for 30 days, unless custom retention rules are applied.
  - Cannot be deleted, but the _Default log sink can be disabled.

### Log Storage Statistics

The Logs Storage page displays a summary of statistics for the logs your project is receiving, including:

- **Current total volume**: The amount of logs received since the first date of the current month.
- **Previous month volume**: The amount of logs received in the last calendar month.
- **Projected volume by EOM**: The estimated amount of logs by the end of the current month, based on current usage.
- **Total usage by resource type**: Viewable through Metrics Explorer, which lets you build charts for any metric collected by your project.

### Log Export Use Cases

Log Router sinks can forward copies of some or all log entries to non-default locations for:

- Storing logs for extended periods.
- Querying logs with SQL.
- Access control.

### Sink Locations

- **Cloud Logging bucket**: Pre-separate log entries into a distinct log storage bucket.
- **BigQuery dataset**: Use SQL query power of BigQuery for large and complex log entries.
- **Cloud Storage bucket**: Simple external Cloud Storage location for long-term storage or processing with other systems.
- **Pub/Sub topic**: Export log entries to message handling third-party applications or systems like Dataflow or Cloud Functions.
- **Splunk**: Integrate logs into existing Splunk-based systems.
- **Other project**: Control access to a subset of log entries.

### Creating Log Sinks

- Write a query in Logs Explorer to select the log entries you want to export.
- Choose a destination: Cloud Storage, BigQuery, or Pub/Sub.
- The query and destination are held in an object called a sink.
- Sinks can be created in Google Cloud projects, organizations, folders, and billing accounts.

### Creating Exclusion Filters

- Use Logs Explorer to build a query that selects the logs you want to exclude.
- Save the query for building the exclusion.
- Create an exclusion filter to filter unwanted entries out of the sink.
- Give the exclusion a name and add the filter for log entries to exclude.
- Exclusions go into effect immediately and excluded log events will be lost forever.

## Log Aggregation Levels

There are three available Google Cloud Logging aggregation levels:

1. **Project-Level Log Sink**:
   - Exports all logs for a specific project.
   - A log filter can be specified in the sink definition to include/exclude certain log types.

2. **Folder-Level Log Sink**:
   - Aggregates logs on the folder level.
   - Can include logs from children resources (subfolders, projects).

3. **Organization-Level Log Sink**:
   - Aggregates logs on the organization level.
   - Can include logs from children resources (subfolders, projects).

## Security Analytics

Security practitioners onboard Google Cloud logs for security analytics to help prevent, detect, and respond to threats like malware, phishing, ransomware, and poorly configured assets.

### Security Log Analytics Workflow

- Create aggregate sinks and route logs to a single destination depending on the choice of security analytics tool (e.g., Log Analytics, BigQuery, Chronicle, or third-party SIEM technology).
- Logs are aggregated from your organization, including any contained folders, projects, and billing accounts.

### Naming Conventions for Log Entry Fields

- For log entry fields that are part of the LogEntry type, the corresponding BigQuery field names are the same as the log entry fields.
- For user-supplied fields, the letter case is normalized to lowercase, but the naming is otherwise preserved.
- For fields in structured payloads, as long as the @type specifier is not present, the letter case is normalized to lowercase, but naming is otherwise preserved.
- For information on structured payloads where the @type specifier is present, see the Payload fields with @type documentation.

  - Example: Search the last three days (today -2) of the syslog and apache-access logs for a specific Compute Engine instance ID.
- **BigQuery Example**: Look for unsuccessful App Engine requests from the last month.
  - Example: Construct the table data range in the from clause and examine the HTTP status for anything that isn't 200 (successful response).

### Logs Explorer Interface

The Logs Explorer interface lets you retrieve logs, parse and analyze log data, and refine your query parameters. It contains the following panes:

- **Action Toolbar**: Refine logs to projects or storage views, share a link, and learn about Logs Explorer.
- **Query Pane**: Build queries, view recently viewed and saved queries, and more.
- **Results Toolbar**: Quickly show or hide logs and histogram pane, and create a log-based metric or alert.
- **Jump to Now**: Helps query and view the current time results.
- **Query Results**: Details of results with a summary and timestamp to help troubleshoot further.
- **Log Fields Pane**: Filter options based on various factors such as resource type, log name, project ID, etc.
- **Histogram**: Visualize query results as histogram bars, where each bar represents a time range and is color-coded based on severity.

- **Drop-down Menus**

- **Clicking Fields in the Results**

- **Log Name**: Specify `logName`. Select multiple log names at once to add to the Query builder.

## Log Collection

The Google Cloud platform logs visible to you in Cloud Logging vary depending on which Google Cloud resources you're using in your project or organization. Let's explore the key log categories:

### Key Log Categories

1. **Platform Logs**: 
   - Written by Google Cloud services.
   - Help debug and troubleshoot issues.
   - Example: VPC Flow Logs record a sample of network flows sent from and received by VM instances.

2. **Component Logs**: 
   - Generated by Google-provided software components running on your systems.
   - Example: GKE provides software components that users can run on their own VM or in their own data center. Logs are generated from the user's GKE instances and sent to a user's Cloud project.

3. **Security Logs**: 
   - Help answer "who did what, where, and when."
   - **Cloud Audit Logs**: Provide information about administrative activities and accesses within your Google Cloud resources.
   - **Access Transparency**: Logs actions taken by Google staff when accessing your Google Cloud content.

4. **User-Written Logs**: 
   - Written by custom applications and services.
   - Typically written to Cloud Logging using Ops Agent, Cloud Logging API, or Cloud Logging client libraries.
   - Can be sent programmatically using client libraries or Logging agents.
   - Example: In container environments like Google Kubernetes Engine or Container-Optimized OS, agents automatically collect logs from stdout and stderr.
   - On VMs, agents collect logs from known file locations or logging services like the Windows Event Log, journald, or syslogd.
   - Serverless compute services like Cloud Run and Cloud Functions include simple runtime logging by default. Logs written to stdout or stderr will appear automatically in the Google Cloud console.

## Task 3: Manage Log Buckets

There are two ways you can enable Log Analytics. One way is to upgrade an existing bucket. The other is to create a new log bucket with Log Analytics enabled.

### Upgrade an Existing Bucket

You can use the following steps to upgrade an existing log bucket.

1. On the Navigation menu, click **Logging**, then click **Logs Storage**.
2. Click **UPGRADE** for an existing bucket, for example, the _Default bucket.
3. Click **UPGRADE** in the popup window.
4. Wait for the upgrade to complete. Initially, the status changes to **Not eligible for upgrade** before you see the **Upgraded** status.
5. Click the **OPEN** dropdown button.
6. Select the view _AllLogs, the Log Analytics page will open for you.

### Create a New Log Bucket

Alternatively, you can configure Cloud Logging to create a new log bucket with Log Analytics enabled.

1. On the left-hand menu, open **Logging**, then click **Logs Storage**.
2. Click **CREATE LOG BUCKET** at the top.
3. Provide a name such as `day2ops-log` to the bucket.
4. Check both **Upgrade to use Log Analytics** and **Create a new BigQuery dataset that links to this bucket**.
5. Type in a dataset name such as: `day2ops_log`.
6. Finally, click **Create bucket** to create the log bucket.

### Write to the New Log Bucket

You can create a log sink to use the new log bucket. You can do it from the Logs Router directly. Another easy way to do this is from Logs Explorer. You can run log queries to select and filter the logs you are interested in and create a sink. One nice thing about that approach is the log query will be automatically copied to the sink configuration as the filter.

1. On the Navigation menu, click **Logging**, then click **Logs Explorer**.
2. In the top-right of Logs Explorer, enable **Show query** and run the following query in the query field:

    ```sh
    resource.type="k8s_container"
    ```

3. Click on **Actions** then click **Create sink**.
4. Provide a name such as `day2ops-sink` as the sink name.
5. Click **NEXT**.
6. Select **Logging bucket** in the sink service dropdown list.
7. Select the new log bucket you just created.
8. Click **NEXT**.
9. You should see the resource type query already in the filter.
10. Click **CREATE SINK**.
11. Wait a little bit and your sink should be created.

### Read from the New Log Bucket

1. Go back to the **Logs Explorer**. Notice that there are many different resource types for the logs.
2. To view the logs in the new log bucket, click **REFINE SCOPE** at the top of the page.
3. Select **Log view** and the new log bucket you just created.
4. Click **APPLY**.
5. You will see **Kubernetes Containers** is now the only resource type and there are much fewer log entries now. That's because only filtered logs will be sent to the bucket.

### To Find the Most Recent Errors

You want to find the most recent errors from the containers:

```sql
SELECT
 TIMESTAMP,
 JSON_VALUE(resource.labels.container_name) AS container,
 json_payload
FROM
 `"PROJECT_ID".global.day2ops-log._AllLogs`
WHERE
 severity="ERROR"
 AND json_payload IS NOT NULL
ORDER BY
 1 DESC
LIMIT
 50
```

After running the query, you should see the output like the following:

```sh
!Query Results
```

### To Find the Min, Max, and Average Latency

You can view the min, max, and average latencies in a timeframe for the frontend service:

```sql
SELECT
hour,
MIN(took_ms) AS min,
MAX(took_ms) AS max,
AVG(took_ms) AS avg
FROM (
SELECT
  FORMAT_TIMESTAMP("%H", timestamp) AS hour,
  CAST( JSON_VALUE(json_payload,
      '$."http.resp.took_ms"') AS INT64 ) AS took_ms
FROM
  `"PROJECT_ID".global.day2ops-log._AllLogs`
WHERE
  timestamp > TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 24 HOUR)
  AND json_payload IS NOT NULL
  AND SEARCH(labels,
    "frontend")
  AND JSON_VALUE(json_payload.message) = "request complete"
ORDER BY
  took_ms DESC,
  timestamp ASC )
GROUP BY
1
ORDER BY
1
```

After running the query, you should see the output like the following:

```sh
!Query Results
```

### Product Page Visit Number

You want to know how many times users visit a certain product page in the past hour:

### Sessions with Shopping Cart Checkout

You can run the following query to view how many sessions end up with checkout (POST call to the /cart/checkout service):

```sql
SELECT
 JSON_VALUE(json_payload.session),
 COUNT(*)
FROM
 `"PROJECT_ID".global.day2ops-log._AllLogs`
WHERE
 JSON_VALUE(json_payload['http.req.method']) = "POST"
 AND JSON_VALUE(json_payload['http.req.path']) = "/cart/checkout"
 AND timestamp > TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 1 HOUR)
GROUP BY
 JSON_VALUE(json_payload.session)
```
