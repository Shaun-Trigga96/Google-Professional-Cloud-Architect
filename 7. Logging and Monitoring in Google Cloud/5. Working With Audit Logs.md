# Cloud Audit Logs

## Overview

In this module, we will investigate the core Cloud Audit Logs that Google Cloud collects.

### Learning Objectives

Upon completion of this module, you will be able to:

- Explain Cloud Audit Logs.
- Describe different types of audit logs, their features, and functionalities.
- Implement best practices for using audit logs effectively.

## Working with Cloud Audit Logs

In this module, we start with an overview of what audit logs do for us. Then we move to using the optional Data Access audit logs, explore the format of audit log entries, and wrap up with some logging best practices.

### Importance of Cloud Audit Logs

In terms of sheer volume of useful information, probably the most important group of logs in Google Cloud are the Cloud Audit Logs. They help answer the question, "Who did what, where, and when?"

### Types of Cloud Audit Logs

Cloud Audit Logs maintain four types of audit logs for each Google Cloud project, folder, and organization:

1. **Admin Activity Audit Logs**:
    - Contain log entries for API calls or other administrative actions that modify the configuration or metadata of resources.
    - Examples: Creating VM instances, changing IAM permissions.
    - Always on, retained for 400 days, available at no charge.
    - Viewing requires IAM role `Logging/Logs Viewer` or `Project/Viewer`.

2. **System Event Audit Logs**:
    - Contain log entries for Google Cloud administrative actions that modify the configuration of resources.
    - Generated by Google systems, not driven by direct user action.
    - Always enabled, free, retained for 400 days.
    - Viewing requires IAM role `Logging/Logs Viewer` or `Project/Viewer`.

3. **Data Access Audit Logs**:
    - Contain API calls that read the configuration or metadata of resources, and user-driven API calls that create, modify, or read user-provided resource data.
    - Do not record data-access operations on publicly shared resources or resources accessed without logging into Google Cloud.
    - Disabled by default (except for BigQuery), with a default retention of 30 days when enabled.
    - Viewing requires IAM roles `Logging/Private Logs Viewer` or `Project/Owner`.

4. **Policy Denied Audit Logs**:
    - Record when access to a user or service account is denied by a Google Cloud service due to a security policy violation.
    - Generated by default, and your Google Cloud project is charged for the logs storage.
    - Cannot be disabled, but exclusion filters can prevent these logs from being ingested and stored in Cloud Logging.

### Viewing and Filtering Audit Logs

To view and filter audit logs:

1. Navigate to **Logs Explorer**.
2. Filter by using the **Log name** drop-down menu.
3. Typing `cloudaudit` into the filter box is often quicker than scrolling.
4. If one of the four audit logs is missing, it means it doesn’t currently have any entries.
5. Use the query builder to filter audit logs. This query is auto-populated in the query section when using the UI.

### Access Transparency Logs

Similar to Cloud Audit Logs, Access Transparency logs provide logs of accesses to your data by human Googlers (as opposed to automated systems). Enterprises with appropriate support packages can enable these logs and receive the log events in near-real time. The log events are surfaced through the APIs, Cloud Logging, and Security Command Center.

- **Cloud Audit Logs**: Record actions taken by members of your Google Cloud organization.
- **Access Transparency Logs**: Record actions taken by Google personnel.

### Data Access Audit Logs

#### Enabling Data Access Audit Logs

Data Access audit logs can be enabled at various levels in the resource hierarchy:

- Organization
- Folder
- Project
- Resources
- Billing accounts

You can also exempt principals from recording data access logs. The final configuration of Data Access audit logs is the union of the configurations. For example, at a project level, you can enable logs for a Google Cloud service, but you can't disable logs for a service that is enabled in a parent organization or folder.

#### Cost

The added logging does add to the cost, currently: $0.50 per gigabyte for ingestion.

#### Default Settings

Data Access audit logs are disabled by default, except for BigQuery. They may be enabled and configured at the organization, folder, project, or service level.

#### Types of Data Access Audit Logs

You can control what type of information is kept in the audit logs. There are three types of Data Access audit logs information:

1. **Admin-read**: Records operations that read metadata or configuration information. For example, viewing the configurations for your bucket.
2. **Data-read**: Records operations that read user-provided data. For example, listing files and downloading one from Cloud Storage.
3. **Data-write**: Records operations that write user-provided data. For example, creating a new Cloud Storage file.

#### Exemptions

You can exempt specific users or groups from having their data accesses recorded. This functionality helps reduce the cost and noise associated with the volume of logs that are not of your interest. Data Access audit logs can be of high volume, so the cost is directly proportional to the volume of data logs.

#### Enabling Data Access Audit Logs via CLI or API

You can use the Google Cloud CLI or the API to enable Data Access audit logs. If you're using the `gcloud` CLI frequently, the easiest way is to:

1. Get the current IAM policies and write them to a file.
2. Edit the `/tmp/policy.yaml` file to add or edit the `auditLogConfigs`.
3. Add the log details per service, like enabling logging for Cloud Run, or enable logging on all services.
4. Set that as the new IAM policy.

### Examining Logging Entries

Now that you've learned to enable the logs you need, let’s examine the logging entries themselves.

#### LogEntry Object

Every audit log entry in Cloud Logging is an object of type `LogEntry`. What distinguishes an audit log entry from other log entries is the `protoPayload` field, which contains an `AuditLog` object that stores the audit logging data.

#### Key Fields in Audit Log Entries

- **Log Name**: Indicates the type of audit log (e.g., Data Access audit logs).
- **principalEmail**: Identifies the principal generating the log.
- **operation**: Exists only for large or long-running audit log entries.

#### Service Names

Google has a standard list of official service names, which can be used as a handy reference.

#### Example: BigQuery Query

In the example of a query run in BigQuery:

- The `serviceData` field can be expanded to see the actual query.
- This allows you to identify who ran the query and what the query was, which is useful for tracking unexpected or costly queries.

### Best Practices for Data Access Audit Logs

#### Planning and Implementation

1. **Start with Planning**:
    - Spend time creating a solid plan for Data Access audit logs.
    - Think in terms of organization, folder, then project.

2. **Create a Test Project**:
    - Experiment to see if the logging works as expected before rolling out the plan.

3. **Automation**:
    - Use Infrastructure as Code (IaC) to automate the creation and modifications to your infrastructure.
    - Tools like Terraform can help manage configurations and state management.

#### Enabling Data Access Audit Logs 2

- **Enable at the Organization Level**:
  - Provides detailed information on who accessed, edited, and deleted what, and when.
  - Be aware of the potential for large log volumes and associated costs.

#### Infrastructure as Code (IaC)

- **Automate with IaC**:
  - Automate infrastructure using platforms that support configuration files.
  - Use CI/CD pipelines to manage these configurations.

- **State Management**:
  - Decide between remote (e.g., Cloud Storage, Terraform Cloud) or local state management.

#### Managing Logs

- **Aggregate Logs**:
  - Aggregate logs from across your organization into a single Cloud Logging bucket.
  - Create user-defined buckets to centralize or subdivide log storage.

- **Customize Log Storage**:
  - Define where logs are stored and set data retention periods based on compliance and usage requirements.
  - Configure default storage locations to meet latency, compliance, and availability requirements.

- **Encryption**:
  - Use customer-managed encryption keys (CMEK) if advanced encryption requirements are needed.

#### Exporting Logs

- **Plan Exports**:
  - Decide what to export from Aggregated Exports at the organization level.
  - Consider filters carefully to manage what is included or excluded from logs.

#### Access Control

- **Use IAM Controls**:
  - Apply appropriate IAM controls to both Google Cloud-based and exported logs.
  - Limit access to the minimum required to perform necessary tasks.

- **Protect Sensitive Data**:
  - Scrutinize Data Access audit log permissions, as they often contain Personally Identifiable Information (PII).
  - Use log views to control access to logs in a log bucket.

#### Access Scenarios

- **Operational Monitoring**:
  - Assign appropriate roles to high-level teams and individuals.
  - Use IAM to secure access to data exported to Cloud Storage or BigQuery.

- **Development Teams**:
  - Provide necessary logging roles at the folder level for development projects.
  - Limit data used in testing to avoid exposing actual customer information.

- **External Auditors**:
  - Provide pre-created dashboards where possible.
  - Use IAM roles to control access to logs and exported data.

By following these best practices, you can effectively manage and utilize Data Access audit logs while maintaining security and compliance.
